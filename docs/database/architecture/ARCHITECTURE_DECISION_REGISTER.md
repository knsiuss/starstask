## AD-01 — Class/cohort naming

| Field                    | Value                                                                                                                                                                                                                                                      |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Decision ID**          | AD-01                                                                                                                                                                                                                                                      |
| **Current state**        | Cohort table is `classes`, PK `id uuid`, with `slug` and `class_code` (nullable, normalized via generated `class_code_normalized`). Referenced by 20+ tables via `class_id` FKs (VERIFIED: every core-domain table carries `class_id`).                    |
| **Evidence**             | `pg_constraint contype='f' AND confrelid='classes'` — 20 FKs point at `classes(id)`. `classes_pkey`, `classes_slug_key`. Migration `20261029000900_classes.sql` created the table.                                                                         |
| **Problem**              | Name `classes` collides with `courses` and `class_subjects` (three similar names, three concepts). In multi-university readings, "class" is ambiguous (course offering vs cohort vs section).                                                              |
| **Proposed direction**   | Docs-first rename to `class_cohorts` with a DB view/alias shim (`CREATE VIEW classes AS SELECT * FROM class_cohorts`) kept for compatibility, or Postgres table alias via view. Rename table + add view; keep old name working indefinitely.               |
| **Alternatives**         | (a) Keep `classes` and document it as "cohort" forever — zero DDL, best compatibility. (b) Rename to `cohorts` (drops the `class_` prefix but breaks every `class_id` FK name). (c) Add a `cohorts` table and migrate — highest cost, no benefit over (a). |
| **Impacted objects**     | `classes` (1 table), 20 FKs, 7 indexes, 12+ policies, ~40 functions referencing `classes` columns, `class_id` columns on 20+ tables, generated types + `apps/web/src/types/database.ts`.                                                                   |
| **Application impact**   | Classes, memberships, attendance, assignments, leave, notifications, admin pages — effectively the whole app.                                                                                                                                              |
| **Migration complexity** | High                                                                                                                                                                                                                                                       |
| **Compatibility risk**   | High                                                                                                                                                                                                                                                       |
| **Rollback strategy**    | Reversible: rename back + drop shim view in one migration. Pre-rename backup required.                                                                                                                                                                     |
| **Approval status**      | Pending                                                                                                                                                                                                                                                    |

## AD-02 — Course catalogue naming

| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Decision ID**          | AD-02                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Current state**        | Global catalogue `courses` (`id uuid`, `name`, `code`, `department`, `normalized_name` UNIQUE, `normalized_code`). Public read policy `courses_public_read` (`USING (true)`). Referenced by `classes.course_id` (NOT NULL, RESTRICT), `assignments.course_id` (NOT NULL, RESTRICT), `class_subjects.course_id` (nullable, SET NULL) — all VERIFIED in both environments. Origin: `20261029000100_core_schema.sql:84`. |

App usage: `create_or_get_course` RPC, `list_assignments` with `p_course_id`.                                                                                                                                                                                                                                           |

| **Application impact**   | Course creation, assignment publishing, class creation, schedule import matcher.                                                                                                                                                                                                                                                                                                                                      |

| **Rollback strategy**    | Rename-back migration; no data change.                                                                                                                                                                                                                                                                                                                                                                                |

## AD-03 — Class subject naming

| Field                    | Value                                                                                                                                                                                                                        |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Decision ID**          | AD-03                                                                                                                                                                                                                        |
| **Current state**        | `class_subjects` (`class_id` NOT NULL CASCADE, `course_id` nullable SET NULL, own `name`/`code`/`lecturer_name`, `status active                                                                                              | archived`). PK `id uuid`. Children via `subject_id`: assignments, sessions, schedules, materials, calendar events, correction audits. Unique `class_subjects_class_code_uniq`on`(class_id, lower(btrim(code)))` where code not null. |
| **Evidence**             | 6 FKs into `class_subjects(id)`; trigger `ensure_subject_in_class` enforces subject belongs to the same class on assignments/sessions/schedules/materials/calendar.                                                          |
| **Problem**              | Name reads as a junction table but it is a first-class entity (the class's offering of a catalogue course). It carries both catalogue link (`course_id`, nullable) and class-local identity (`name`/`code`/`lecturer_name`). |
| **Proposed direction**   | Docs-first: document as "class course offering". If renamed, prefer `class_courses` + view shim. Separately decide whether `course_id` should become NOT NULL (catalogue-required) or stay optional for ad-hoc subjects.     |
| **Alternatives**         | (a) Keep + document. (b) `class_courses` + shim. (c) Split catalogue-linked vs ad-hoc subjects into two tables — doubles subject logic, not justified.                                                                       |
| **Impacted objects**     | `class_subjects` (1 table), 6 child FKs, 4 indexes, 3 policies, subject CRUD RPCs, attendance RPCs (`class_attendance_recap` takes `p_subject_id`), sheet/export code.                                                       |
| **Application impact**   | Course workspace, attendance sheet, assignments, schedule import, materials, calendar.                                                                                                                                       |
| **Migration complexity** | High (if renamed) / None (if kept)                                                                                                                                                                                           |
| **Compatibility risk**   | High                                                                                                                                                                                                                         |
| **Rollback strategy**    | Rename-back migration.                                                                                                                                                                                                       |
| **Approval status**      | Pending                                                                                                                                                                                                                      |

## AD-04 — Discussion session domain separation

| Field                    | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Decision ID**          | AD-04                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Current state**        | `discussion_sessions` serves two roles: (1) discussion/session scheduling (RSVP, reminders, Google Calendar mapping, `assignment_id` link) and (2) attendance meetings (`subject_id` + `meeting_number` both-or-neither CHECK `discussion_sessions_meeting_identity`, `meeting_date`, `attendance_*` lifecycle columns, check-in geo columns, `late_after_minutes` NOT NULL default 10).                                                                                                                                                            |
| **Evidence**             | 21 CHECK constraints on the table; `attendance_*` and check-in columns present; unique `discussion_sessions_class_subject_meeting_uniq (class_id, subject_id, meeting_number)` for the meeting role; functions split into session RPCs (`create_discussion_session`, `rsvp_discussion_session`) and attendance RPCs (`create_attendance_meeting`, `check_in_attendance_meeting`, `class_attendance_recap`) all reading the same table. App: `features/attendance-meetings/meeting-service.ts` calls attendance RPCs; session UI calls session RPCs. |
| **Problem**              | Attendance logic (identity-verified GPS check-in, roster, recap, XLSX) is coupled to scheduling; a change to session fields risks attendance behavior and vice versa. The brief explicitly forbids merging entities on naming similarity alone — but here the coupling is real (shared table, shared triggers).                                                                                                                                                                                                                                     |
| **Proposed direction**   | Keep one table; strengthen the boundary in code/RPCs (attendance RPCs only touch meeting-role rows via `meeting_number IS NOT NULL`; session RPCs reject meeting-role rows). Split only when a measured need appears (e.g. session volume ≫ meeting volume causing index bloat).                                                                                                                                                                                                                                                                    |
| **Alternatives**         | (a) Keep + enforce role checks in RPCs — low cost. (b) New `attendance_meetings` table + dual-write migration — HIGH complexity, two sources of truth during cutover. (c) View-per-role (`discussion_sessions` + `attendance_meetings` view) — cosmetic only.                                                                                                                                                                                                                                                                                       |
| **Impacted objects**     | `discussion_sessions`, `discussion_session_checkins`, `discussion_session_rsvps`, `discussion_session_reminders`, `attendance_correction_audits`, `attendance_verification_attempts`, `google_calendar_event_mappings`, 8 indexes, 4 triggers, ~15 RPCs.                                                                                                                                                                                                                                                                                            |
| **Application impact**   | Sessions, attendance check-in, recap/export, reminders, calendar sync.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Migration complexity** | High (if split) / Low (if RPC role checks only)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Compatibility risk**   | High (if split) / Low (if RPC checks only)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Rollback strategy**    | For split: backfill + cutover flag, rollback = revert read path. For RPC checks: revert function bodies.                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **Approval status**      | Pending                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## AD-05 — Assignment ownership and scope

| Field                    | Value                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Decision ID**          | AD-05                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Current state**        | `assignments` carries three scope FKs: `course_id` NOT NULL RESTRICT (catalogue), `class_id` nullable SET NULL, `subject_id` nullable SET NULL. Plus `user_id` NOT NULL CASCADE (owner), `reviewed_by`, `status` (7-value CHECK), `content_type` (`lecturer_assignment`                                                                                                                                                                             | `class_announcement`), `assignment_type` (nullable CHECK). Triggers `ensure_subject_active` + `ensure_subject_in_class` enforce subject consistency with class. |
| **Evidence**             | 4 FKs, 10 indexes (incl. `assignments_class_idx`, `assignments_subject_idx` partial, `assignments_review_queue_idx` partial), 8 policies, 8 triggers (VERIFIED `\d+ public.assignments`). `list_assignments` doc: "A class filter includes the class's own assignments and published class-less assignments in the same catalog courses."                                                                                                           |
| **Problem**              | Triple-scope rows are ambiguous: a `class_id`-null, `course_id`-set assignment is "public catalogue"; with `class_id` set it is "class assignment"; `subject_id` narrows further. No CHECK enforces that `subject_id` implies `class_id`, nor that `course_id` matches the class's `course_id`. The public-read policy (`class_id IS NULL` + published) vs class-member-read policy (`class_id IS NOT NULL`) makes scope load-bearing for security. |
| **Proposed direction**   | Document scope precedence: `subject_id` > `class_id` > `course_id`-only (public). Add CHECKs: `subject_id IS NULL OR class_id IS NOT NULL` and trigger-level validation that `course_id` matches the class/subject catalogue course. Long-term: split public-catalogue assignments from class assignments if the public discovery feature grows.                                                                                                    |
| **Alternatives**         | (a) CHECKs + triggers only — low complexity. (b) NOT NULL scope discriminator column + backfill — medium. (c) Split into `public_assignments` / `class_assignments` — high complexity, breaks `list_assignments` and all assignment RPCs.                                                                                                                                                                                                           |
| **Impacted objects**     | `assignments` (1 table), 10 indexes, 8 policies, 3 assignment RPCs + `list_assignments`, `record_assignment_revision` trigger, notification claim RPCs.                                                                                                                                                                                                                                                                                             |
| **Application impact**   | Assignment publishing/review, public browsing, class course page, notifications.                                                                                                                                                                                                                                                                                                                                                                    |
| **Migration complexity** | Low (CHECKs/triggers) / High (split)                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Compatibility risk**   | Medium — invalid historical rows would block a new CHECK; backfill/audit first.                                                                                                                                                                                                                                                                                                                                                                     |
| **Rollback strategy**    | Drop CHECK/trigger (no data change).                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Approval status**      | Pending                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## AD-06 — Academic term representation

| Field                    | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Decision ID**          | AD-06                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Current state**        | Term data lives in three places: `classes.semester` (NOT NULL text) + `classes.academic_year` (NOT NULL, CHECK `YYYY/YYYY`); `class_course_schedules.period` (nullable text) + `start_date`/`end_date` (nullable date) added 20261105; `assignments.semester`/`academic_year` (both nullable). No term entity, no FK.                                                                                                                                               |
| **Evidence**             | VERIFIED column dumps both environments. `classes_period_code_key` UNIQUE on `(class_code_normalized, academic_year, semester, COALESCE(institution_normalized,''))` where code not null; `classes_period_idx (academic_year, semester, status)`. `class_course_schedules` period columns verified (14 columns incl. `period`, `start_date`, `end_date`). Contracts: `packages/contracts/src/classes.ts` (`semester`, `institution`), `assignment.ts` (`semester`). |
| **Problem**              | `classes.semester` is the class identity term; `class_course_schedules.period` is the timetable validity term; `assignments.semester` is denormalized display text. Three representations of "term" can drift. `semester` is free text (length 1–20 only).                                                                                                                                                                                                          |
| **Proposed direction**   | Keep two scoped concepts but unify format: validate `semester` against a shared pattern (e.g. `1`-`14` or `Ganjil`/`Genap`, decided with the university) and document that schedule `period` is a display label for the schedule's date range, not a second class term. Add a future `academic_terms` entity only if multi-semester reporting is required.                                                                                                          |
| **Alternatives**         | (a) Format validation + docs — low. (b) `academic_terms` table + FKs on `classes`/`class_course_schedules`/`assignments` — medium, touches uniqueness `classes_period_code_key`. (c) Merge schedule `period` into `classes.semester` — loses per-schedule validity ranges, not recommended.                                                                                                                                                                         |
| **Impacted objects**     | `classes`, `class_course_schedules`, `assignments`, `class_applications` (has `semester`/`academic_year`), 4 indexes, uniqueness constraint, `list_classes`, `list_platform_classes`, `find_class_duplicates`.                                                                                                                                                                                                                                                      |
| **Application impact**   | Class creation, schedule import/display, assignment listing, admin filters.                                                                                                                                                                                                                                                                                                                                                                                         |
| **Migration complexity** | Low (validation) / Medium (entity)                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Compatibility risk**   | Medium — existing free-text `semester` values must be audited before any CHECK.                                                                                                                                                                                                                                                                                                                                                                                     |
| **Rollback strategy**    | Drop CHECK (no data change).                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Approval status**      | Pending                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## AD-07 — Institution → university relationship

| Field                    | Value                                                                                                                                                                                                                                                                                                                              |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Decision ID**          | AD-07                                                                                                                                                                                                                                                                                                                              |
| **Current state**        | `classes.institution` is nullable free text (length 2–120). Generated `institution_normalized` feeds uniqueness. No `universities` table, no `university_id` anywhere in `public` (VERIFIED column grep). `class_applications.institution` mirrors the free text. `courses` has `department` (free text) but no institution link.  |
| **Evidence**             | VERIFIED: `information_schema` grep for `university_id                                                                                                                                                                                                                                                                             | tenant_id`empty;`classes_institution_length`CHECK;`classes_period_code_key`includes`institution_normalized`. Contracts: `classes.ts` `institution: optionalText(...)`. |
| **Problem**              | Every tenant boundary in the future SaaS model must hang off something; today there is nothing to hang off. Two classes with the same institution spelled differently are different "institutions" for uniqueness purposes.                                                                                                        |
| **Proposed direction**   | Introduce `universities` (tenant root) + `university_memberships` (user↔university), then `university_id NOT NULL` on tenant-owned tables (`classes` first), backfilled from `institution` by exact normalized match with manual review for mismatches. Class Admin stays class-scoped; add University Admin role at tenant scope. |
| **Alternatives**         | (a) Keep free text + document — zero DDL, blocks multi-tenancy. (b) `institution` → FK to `universities` with `classes.institution` dropped after backfill — same target, cleaner end-state. (c) Tenant = `institution_normalized` string as the key — fragile, not recommended.                                                   |
| **Impacted objects**     | All 52 tables (tenant column or explicit global classification), 83 public policies, 159 functions, 5 storage buckets (tenant prefix), `class_applications`, `find_class_duplicates`, `list_classes`.                                                                                                                              |
| **Application impact**   | Entire app: auth/session tenant resolution, every RLS policy, every RPC, storage paths.                                                                                                                                                                                                                                            |
| **Migration complexity** | High                                                                                                                                                                                                                                                                                                                               |
| **Compatibility risk**   | High — single-tenant RLS must remain as fallback until tenant resolution is proven.                                                                                                                                                                                                                                                |
| **Rollback strategy**    | Pre-migration verified backup; column nullable first, then NOT NULL after backfill; rollback = restore + keep single-tenant policies.                                                                                                                                                                                              |
| **Approval status**      | Pending                                                                                                                                                                                                                                                                                                                            |

## AD-08 — Tenant-aware uniqueness and relationships

| Field                    | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Decision ID**          | AD-08                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Current state**        | All uniqueness is global: `courses_normalized_name_key`, `classes_period_code_key`, `classes_slug_key`, `class_subjects_class_code_uniq`, `discussion_sessions_class_subject_meeting_uniq`. No tenant column participates in any unique index (VERIFIED). RLS predicates reference class membership, never a tenant.                                                                                                                                                                                                         |
| **Evidence**             | Index/unique inventory (VERIFIED both environments). `courses_public_read USING (true)` is global.                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Problem**              | Two universities will share catalogue names, class codes and slugs. Global uniqueness will either block legitimate duplicates or leak cross-tenant existence via unique-violation errors.                                                                                                                                                                                                                                                                                                                                    |
| **Proposed direction**   | Add `university_id` to tenant-owned tables, then re-scope uniques: `(university_id, normalized_name)` on `courses`, `(university_id, class_code_normalized, academic_year, semester, institution_normalized)` on `classes`, `(university_id, slug)` on `classes`, RLS `university_id = current_tenant()` **in addition to** the existing class check. `courses` table gains `university_id` (owned catalogue) or stays global by explicit decision with `USING (university_id IS NULL OR university_id = current_tenant())`. |
| **Alternatives**         | (a) Schema-per-tenant — rejected: Supabase/Postgres schema sprawl, migration ×N. (b) Keep global uniques + case-by-case exceptions — rejected: error-message oracle + false collisions. (c) Application-level tenant filtering without DB uniques — rejected: race conditions, no DB guarantee.                                                                                                                                                                                                                              |
| **Impacted objects**     | `courses`, `classes`, `class_subjects`, `discussion_sessions`, all RLS policies, all RPCs doing class/course lookups, storage bucket prefixes.                                                                                                                                                                                                                                                                                                                                                                               |
| **Application impact**   | Class creation (slug/code collision UX), course creation, schedule import matching, public browsing.                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Migration complexity** | High                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Compatibility risk**   | High — existing rows need tenant assignment before NOT NULL; duplicate names across tenants are the _goal_, so validation queries must run before constraint swap.                                                                                                                                                                                                                                                                                                                                                           |
| **Rollback strategy**    | Pre-migration backup; new uniques alongside old (dual-unique period), drop old after verification.                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Approval status**      | Pending                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
