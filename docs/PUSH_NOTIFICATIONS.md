# Web Push notifications — StarsTask

## 1. Scope

StarsTask sends **deadline reminders** for assignments a signed-in user owns or
explicitly saved. It is opt-in per user and per device. Nothing is sent to anonymous
visitors, and a save never changes the public assignment.

| Piece           | Location                                                             |
| --------------- | -------------------------------------------------------------------- |
| PWA manifest    | `apps/web/src/app/manifest.ts` → `/manifest.webmanifest`             |
| Service worker  | `apps/web/public/sw.js` → `/sw.js` (scope `/`)                       |
| Registration    | `apps/web/src/components/pwa/service-worker-registration.tsx`        |
| Settings UI     | `apps/web/src/app/settings/notifications/page.tsx`                   |
| Scheduler       | `apps/web/src/app/api/cron/deadline-reminders/route.ts`              |
| Orchestration   | `apps/web/src/lib/push/scheduler.ts`                                 |
| Sender          | `apps/web/src/lib/push/sender.ts`                                    |
| Storage adapter | `apps/web/src/lib/push/store.ts`                                     |
| Migrations      | `supabase/migrations/20261029000500_*.sql` … `20261029000700_*.sql`  |
| Icons           | `apps/web/public/icons/` (generated by `scripts/generate-icons.mjs`) |

**Status:** the code, migrations, tests, and documentation are complete. No Supabase

## 2. Request flow

```
User enables notifications
  └─ Notification.requestPermission()          (only from a click)
  └─ registration.pushManager.subscribe(...)   (public VAPID key only)
  └─ POST /api/push/subscriptions              (endpoint + keys)
       └─ register_push_subscription()         (security definer, user from session)
  └─ PATCH /api/push/preferences { pushEnabled: true }

Cron every 10 minutes
  └─ GET /api/cron/deadline-reminders          (Authorization: Bearer CRON_SECRET)
       ├─ list candidate assignments            published, deadline in the next 25h
       ├─ list_reminder_audience()              owners + savers, opted in, active device
       ├─ enqueue notification_deliveries       unique (user, assignment, type, deadline)
       ├─ claim_notification_deliveries()       FOR UPDATE SKIP LOCKED, attempt_count + 1
       ├─ re-validate each claim                deadline changed / unpublished / opt-out
       ├─ web-push send to every active device  TTL 1h, 10s timeout
       └─ complete_notification_delivery()      sent | pending (retry) | failed | skipped
```

## 3. Data model

| Table                      | Purpose                                 | Client access                                      |
| -------------------------- | --------------------------------------- | -------------------------------------------------- |
| `push_subscriptions`       | One row per browser push endpoint       | Own rows; endpoint and keys are **not** selectable |
| `notification_preferences` | Opt-in, reminder windows, time zone     | Own row only                                       |
| `saved_assignments`        | Assignments a user follows              | Own rows only                                      |
| `notification_deliveries`  | Durable reminder ledger and retry state | Own rows, **read-only**                            |

Key constraints:

- `push_subscriptions.endpoint` is unique. Re-registering an endpoint owned by another
  account returns `null` and the API answers `409` without confirming that the endpoint
  exists. Ownership is never transferred.
- `notification_deliveries` has a unique key on
  `(user_id, assignment_id, reminder_type, deadline_at)`. Repeated scheduler runs are
  therefore idempotent, while a **changed deadline** creates a new logical reminder and
  makes the old one stale.
- `notification_deliveries.status` is one of `pending`, `processing`, `sent`, `failed`,
  `skipped`.
- No notification payload, endpoint, or key is stored in the ledger.

Full column list and RLS matrix: `docs/DATABASE.md`.

## 4. Scheduling rules

### Windows

| Reminder | Offset before the deadline |
| -------- | -------------------------- |
| `24h`    | 24 hours                   |
| `3h`     | 3 hours                    |

- Default time zone is `Asia/Jakarta`; the user can choose another IANA zone in settings.
  The zone only affects how the deadline is phrased — the stored deadline is an instant.
- A reminder is enqueued when `now - 1 hour < deadline - offset <= now`. The one-hour grace
  covers a missed or slow cron run without turning a "24 hours left" reminder into a
  "2 hours left" one.
- Candidates are limited to published assignments with a deadline in the next **25 hours**.
- No deadline, deleted, unpublished, or opted-out assignments are excluded.
- Only owners and users with an explicit `saved_assignments` row are in the audience.

### Delivery

- Each claim is re-validated immediately before sending. A changed deadline, a removed
  deadline, an unpublished assignment, a disabled preference, or an invalid payload marks
  the row `skipped` — no stale reminder is sent.
- One logical reminder is sent to **every active device** of the user. The row is `sent`
  when at least one device succeeds.
- `404` / `410` from a push service disables that subscription permanently
  (`disabled_at`), so it stops being loaded.
- `401` / `403`, `429`, `5xx`, timeouts, and network errors are transient. They are
  retried with backoff after **5, 15, then 60 minutes**, up to **3 attempts**. After that
  the row is `failed`.
- `400` / `413` are treated as permanent failures for that delivery but do not disable the
  subscription.
- Push messages use `TTL: 3600`; a push service holding a reminder for longer would deliver
  it after the deadline.
- The worker requeues rows stuck in `processing` for more than 10 minutes, so a crashed
  run cannot strand a reminder.

### Concurrency and dedupe

`claim_notification_deliveries` selects due rows with `FOR UPDATE SKIP LOCKED` and moves
them to `processing` in one statement. Two overlapping cron invocations therefore claim
disjoint batches; the unique ledger key prevents a second logical row for the same
deadline. The service worker also uses a deterministic `tag`
(`starstask:<assignment>:<type>:<deadline>`) so a redelivered push replaces the previous
notification instead of stacking.

## 5. Scheduler deployment

### Vercel Cron

`apps/web/vercel.json` requests:

```json
{
  "crons": [
    { "path": "/api/cron/deadline-reminders", "schedule": "*/10 * * * *" }
  ]
}
```

Vercel sends `Authorization: Bearer $CRON_SECRET` when that variable exists. The route
rejects everything else with `401`, and returns `503` when VAPID or the service-role key is
missing.

**Plan limitation:** the Hobby plan only allows **daily** cron jobs. A 10-minute schedule
requires **Pro**. If the project stays on Hobby, use one of the alternatives below instead
of silently accepting a once-a-day reminder.

### Alternatives

1. **Supabase `pg_cron` + `pg_net`** — schedule an HTTP GET from Postgres:

   ```sql
   select cron.schedule(
     'starstask-deadline-reminders',
     '*/10 * * * *',
     $$
       select net.http_get(
         url := 'https://<your-domain>/api/cron/deadline-reminders',
         headers := jsonb_build_object(
           'Authorization', 'Bearer ' || current_setting('app.cron_secret')
         )
       );
     $$
   );
   ```

   Store the secret in Supabase Vault rather than a plain setting in production. This has
   not been configured or tested here.

2. **External scheduler** (GitHub Actions, cron-job.org, a small worker) — call the same URL
   every 10 minutes with the bearer token. Keep the token in that service's secret store.

3. **Manual run** — useful for local verification:

   ```bash
   curl -fsS -H "Authorization: Bearer $CRON_SECRET" \
     https://<your-domain>/api/cron/deadline-reminders
   ```

The scheduler is independent of page visits. It is **not active** until one of these is
configured on the deployed environment.

## 6. Environment variables

All five values must be set together; the app degrades gracefully (settings shows "not
configured", the cron route returns `503`) when they are absent.

| Variable                    | Scope                 | Notes                                         |
| --------------------------- | --------------------- | --------------------------------------------- |
| `VAPID_PUBLIC_KEY`          | Server → browser prop | Public key; safe to expose                    |
| `VAPID_PRIVATE_KEY`         | Server only           | Never log, never prefix with `NEXT_PUBLIC_`   |
| `VAPID_SUBJECT`             | Server only           | `mailto:` or `https:` URI                     |
| `SUPABASE_SERVICE_ROLE_KEY` | Server only           | Used **only** by the cron route; bypasses RLS |
| `CRON_SECRET`               | Server only           | Bearer token, at least 32 characters          |

Generate VAPID keys once per deployment:

```bash
pnpm --filter @starstask/web exec web-push generate-vapid-keys
```

Generate the cron secret:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

`scripts/check-env.mjs` fails when the push group is partially configured, when
`VAPID_SUBJECT` is not a `mailto:`/`https:` URI, when `CRON_SECRET` is shorter than 32
characters, or when a `NEXT_PUBLIC_VAPID_PRIVATE_KEY` exists.

Rotating VAPID keys invalidates every existing subscription: users must disable and
re-enable notifications. Rotating `CRON_SECRET` only requires updating the scheduler.

## 7. HTTP API

All routes are `no-store` and require a verified session unless marked otherwise.

| Method and path                                | Body                                                          | Result                                                         |
| ---------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------- |
| `POST /api/push/subscriptions`                 | `{ endpoint, keys: { p256dh, auth }, deviceLabel? }`          | `201 { id }`; `409` if the endpoint belongs to another account |
| `DELETE /api/push/subscriptions`               | `{ endpoint }`                                                | `{ removed: boolean }`; idempotent                             |
| `DELETE /api/push/subscriptions/[id]`          | —                                                             | `{ id }`; `404` if not owned                                   |
| `GET /api/push/preferences`                    | —                                                             | `{ preferences, devices }`                                     |
| `PATCH /api/push/preferences`                  | any of `pushEnabled`, `reminder24h`, `reminder3h`, `timezone` | `{ preferences }`; empty patch is rejected                     |
| `GET /api/saved-assignments`                   | —                                                             | `{ saved }`                                                    |
| `POST /api/saved-assignments`                  | `{ assignmentId }`                                            | `201 { assignmentId }`                                         |
| `DELETE /api/saved-assignments/[assignmentId]` | —                                                             | `204`                                                          |
| `GET /api/cron/deadline-reminders`             | Bearer token                                                  | Aggregate counters; `401`/`503` otherwise                      |

Rate limits: subscribe 30/hour, unsubscribe 60/hour, preferences 60/hour, saved
add/remove 120/hour, all per user.

## 8. PWA and service worker

- The manifest is generated by Next.js at `/manifest.webmanifest` with `start_url` and
  `scope` both `/`, `display: standalone`, theme `#1e3a8a`, and 192/512/maskable icons.
- Icons are committed under `apps/web/public/icons/`; regenerate with
  `node scripts/generate-icons.mjs` after changing the brand colour.
- The service worker is served at `/sw.js` with `Service-Worker-Allowed: /` and
  `Cache-Control: no-cache, no-store, must-revalidate`.
- It has **no `fetch` handler and no cache**. Authenticated pages and API responses can
  never be served from a stale or shared cache.
- `push` shows the notification; `notificationclick` focuses an existing same-origin
  window and navigates it to `/assignments/<uuid>`, or opens a new one. The URL is
  validated in the worker because the payload is untrusted by then.
- Registration uses `updateViaCache: "none"` so a deploy cannot leave an old handler in
  place.

### iOS and iPadOS

Web Push on iPhone and iPad requires **iOS/iPadOS 16.4 or later** and the site must be
**added to the Home Screen** and opened from that icon. Safari in a normal tab exposes no
`PushManager`.

The settings page detects this case and shows Add-to-Home-Screen instructions. It does not
render a working "Enable" button there, because the action would fail. iPadOS reports a
desktop Safari user agent; touch points are used to identify it.

No iPhone, iPad, Android, or desktop device was available to test real delivery. Treat the
iOS flow as implemented and reasoned about, not device-verified.

## 9. Security and privacy

- Only the **public** VAPID key reaches the browser, passed as a server-component prop. The
  private key never leaves the scheduler module.
- `SUPABASE_SERVICE_ROLE_KEY` is read only by the cron scheduler. It is not imported by any
  page, client component, or normal API route.
- Endpoints and `p256dh`/`auth` keys are not granted to `authenticated`; the browser already
  knows its own subscription and no UI needs to read another device's endpoint.
- Clients can read their own delivery history but cannot insert or mutate delivery rows.
  `claim_notification_deliveries`, `list_reminder_audience`, and
  `complete_notification_delivery` are executable only by `service_role`.
- The push payload contains a title, body, internal assignment path, tag, icons, and a
  timestamp. It contains no user id, email, storage path, or endpoint.
- Logs contain aggregate counters and error names/categories only — never endpoints,
  payloads, keys, or subscription material.
- RLS is enabled on all four tables; see `docs/SECURITY.md` and `docs/DATABASE.md`.

## 10. Local verification

1. Apply the migrations to a disposable Supabase project (`supabase db push`).
2. Generate VAPID keys and set the five push variables in `apps/web/.env.local`.
3. `pnpm dev`, sign in with Google, open `/settings/notifications`, enable notifications.
4. Save an assignment whose deadline is roughly three hours away (inside the `3h` window).
5. Run the scheduler with a real secret:

   ```bash
   curl -fsS -H "Authorization: Bearer $CRON_SECRET" \
     http://localhost:3000/api/cron/deadline-reminders
   ```

6. Confirm the notification appears, clicking it opens the assignment, and
   `notification_deliveries` shows `sent`.

To exercise retries without a broken push service, temporarily point a subscription at an
invalid endpoint and confirm the row returns to `pending` with `last_error_category =
transient`, then `failed` after three attempts.

Unit tests cover the pure pieces and the whole scheduler against in-memory fakes:

```bash
pnpm --filter @starstask/web test
```

The RLS suite (`pnpm test:integration`) includes push-table cases but has **not** been run
against a live project.

## 11. Troubleshooting

| Symptom                                | Likely cause                                                            | Fix                                                                  |
| -------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------- |
| "Not configured" badge                 | VAPID or service-role env missing                                       | Set all five values, redeploy                                        |
| No "Enable" button on iPhone           | Site opened in Safari, not the Home Screen                              | Add to Home Screen, open the icon, sign in, return to settings       |
| Enable fails with permission denied    | Browser/site notifications blocked                                      | Allow notifications for the origin in browser settings, reload       |
| `409` when enabling                    | Endpoint already registered to another account                          | Disable notifications in the other account, or clear site data       |
| Cron returns `401`                     | `CRON_SECRET` missing or not sent as `Authorization: Bearer …`          | Configure the scheduler's header                                     |
| Cron returns `503`                     | Push env incomplete                                                     | Set VAPID + service-role key                                         |
| Cron returns `200` but nothing arrives | Deadline outside the 24h/3h windows, no active device, or push disabled | Check preferences, device list, and `notification_deliveries.status` |
| Subscription disappears after a send   | Push service returned `404`/`410`                                       | Expected: the endpoint is expired and was disabled                   |
| Duplicate notifications                | Browser kept two subscriptions for the same device                      | Remove the stale device in settings                                  |

## 12. Retention and cleanup

There is **no automatic purge** in this repository. `notification_deliveries` is a ledger
and grows with every reminder and retry. It is small (no payloads), but plan for cleanup.

Safe manual cleanup (terminal rows whose deadline is well in the past):

```sql
delete from public.notification_deliveries
where
  status in ('sent', 'failed', 'skipped')
  and deadline_at < now () - interval '90 days';
```

Do not delete recent terminal rows: the unique key is what prevents a re-send while the
reminder window is still open. A scheduled `pg_cron` job can run the statement above if
long-term retention is required.
